### 2.1 A pre-existing broken test gate was found and repaired (PHASE 0)

`npm run test:full` **failed at the starting HEAD** and the brief did not mention
it. 5 of the 8 `test:cocos` harnesses aborted with `ReferenceError`, and
`test:contracts` never ran at all. All five share one cause: each harness
`esbuild`-transforms a *slice* of a TypeScript file starting at `class X`, so the
file's `import` statements are excluded and every imported symbol becomes an
undefined global.

Repair was test-harness-only — **no assertion weakened, no test deleted, no
production file touched**. `scripts/lib/render_profile_literals.mjs` extracts the
real constants out of `RenderProfile.ts` at test time so the stub cannot drift
from the source.

**Known gap carried forward:** `OPENING_EDIBLE_SPREAD` is stubbed as `[]` in two
harnesses. Stubbing the real 14-entry spread breaks pre-existing exact-census
fixtures that predate it. It therefore remains **untested**. Documented in the
harnesses in-line.

## 3. PHASE 1 — the MaterialLibrary is real

### The three defects found

The previous attempt wrote 8 `.material` files that shipped in **no bundle**.
PHASE 0 isolated three independent causes:

1. They were written to `assets/resources/game_art/materials/` instead of the
   bundle directory `assets/game_art/materials/`.
2. Every `.meta` said `imported: false` — Creator never processed them. **Cause:
   the extension.** Creator's asset database routes materials through `.mtl`
   and the `material` importer; `.material` is silently ignored.
3. Nothing referenced them. In Cocos an asset ships only when something in its
   bundle depends on it — a bare file in a folder is not enough.

### What was built

- `scripts/v7_phase1_materials.mjs` writes 10 materials into
  `cocos/assets/game_art/materials/` as `.mtl`, and removes the stray copies.
  Supersedes and deletes `scripts/v7_generate_materials.mjs`.
- `cocos/assets/game_art/ArtBootstrap.prefab` — `ArtReferenceRoot` with 8
  category children, each holding an `ArtMaterialReference` whose
  `@property(Material)` slots reference the real material uuids. **This prefab is
  what makes the materials ship.**
- `core/MaterialLibrary.ts` loads it non-blocking and merges the 8 holders;
  `core/ArtMaterialReference.ts` is the editor-facing holder.
- `WorldArtLibrary.createRuntimeMaterial` now derives each of the 56 kinds from
  its authored category material via `Material.copy()`, then applies the
  per-kind atlas and `WORLD_PALETTE` tint.

### The design decision that mattered

The brief asks for **7 category materials**; the world has **56 palette entries**
(measured) over **5 colour atlases**, distinguished by a per-kind tint. Collapsing
them into 7 materials would have flattened 56 distinct looks into 7 colours and
destroyed the art.

Resolution: **the authored asset owns the definition** (effect, technique,
blend/depth state, base colour) and the runtime applies the per-kind tint on top
via `Material.copy()`. Seven category templates are the base layer; the tint is a
per-kind variation. This is verified working — the acceptance run shows all 8
categories resident while the 56 kinds keep their own tints.

`MAT_VEGETATION` is an 8th material beyond the brief's 7: trees, hedges and
flowerbeds are a distinct palette category, and leaving them unbound would push
every tree back onto the runtime path this work exists to retire.

### A non-obvious serialisation detail, solved

A prefab component's `__type__` is the script's **compressed** uuid, not its
class name. Writing the class name makes Creator log `Script "..." is missing or
invalid` and **silently drop the component**, leaving `_components: [null]` and
destroying the references. `scripts/lib/cocos_uuid.mjs` implements the
compression, verified by round-trip against the repo's own
`WorldArtLibrary.prefab`. It is a distinct 23-char form from the 22-char uuid used
in built bundle configs — both coexist and must not be mixed.

## 4. PHASE 2 — prefab assetization

### Dead runtime visual generation removed

Deleted after re-verification: `world/WorldChunkManager.ts` (unreachable),
`ui/RoundedPanelGraphic.ts` (uuid in no scene/prefab), `ChunkItemGenerator` from
`world/ChunkConfig.ts` (`CellItemGenerator` kept — it is live), and `MeshFactory`'s
four never-called primitive builders (box/sphere/plane/cone). The home-builder
extension called `getComponentClass('RoundedPanelGraphic')`, which throws once the
class is gone; that lookup is now tolerant.

### Three items the audit wrongly listed as deletable

Re-verification **contradicted** the PHASE 0 report, and the report was corrected:

- `BlackHoleMachine.prefab`, `TrashObject.prefab`, `BedroomChunk.prefab` — no
  *runtime* reference, but `test_cocos_vertical_slice.js:47-49` asserts all three
  **exist**.
- `PolyGoogleBulldozerChassis*.prefab` — referenced by `Game.scene` as
  `cc.PrefabInfo.asset` uuids.
- The `CompressibleObject` runtime lock Label — dead at runtime, but
  `test_vehicle_art_contract.mjs:185-191` reads `TierLockWarning.active` and
  `TierLockLabel.components[0].string`, and the vertical-slice check requires
  `/TierLockWarning/` in the source.

**Lesson recorded in the audit:** "no reference" must be checked against scenes,
prefabs **and test harnesses**, not only runtime code.

### The singularity is now prefab-driven

`BlackHoleMachine` previously built seven runtime primitives at startup and then
**threw them away** when `adoptAuthoredSingularity` swapped in the authored GLB.
It now builds only the node structure and binds the authored mesh + material onto
it. Node identity, names and transforms are unchanged, so the per-frame animation,
the silhouette set and `applyCoreSkin` keep working. `applyCoreSkin` now tints the
authored material instance instead of replacing it with a `MeshFactory` material,
which would have destroyed the asset.

The primitives survive **only** as `activatePrimitiveCoreFallback`, reachable
solely from `onError` — verified by reading the call graph. A missing asset
degrades instead of hiding the player.

### `game_art/prefabs/` — real, loadable assets

`blackhole/ vehicles/ buildings/ props/ collectibles/`, each with a real prefab
wrapping a representative authored asset (mesh sub-asset uuid + authored `.mtl`
uuid), plus `prefabs/manifest.json` mapping 50 `ArtRegistry` artIds and all 56
`WorldArtKind` values to the asset that renders them, generated from the live
registries and the real `Game.scene` template graph (0 unresolved).

### A real bundle-priority defect, found and fixed

`game-art` priority moved **9 → 1**. At 9 it out-ranked `main`, so Creator moved
the shared world meshes the new prefabs reference into `game-art`, making the
always-resident `main` depend on the lazily-loaded bundle and failing boot with
`Please load bundle game-art first`. Priority 0 produced a *broken* config
(`game-art`'s `packs` referenced uuids absent from its `uuids`). At 1:

```
main         deps= ['internal', 'world-city']            uuids= 173
game-art     deps= ['internal', 'main', 'world-city']    uuids= 42
world-city   deps= []                                    uuids= 39
internal     deps= []                                    uuids= 32
```

`main` no longer depends on `game-art`, and there are **0 inconsistent packs**.

## 5. PHASE 4 — the singularity reads as a vortex

Five upgrades, all driven by real state. **No collision, suction radius, mass,
tier or FSM value was touched.**

1. **Suction particles** — authored prefab + `MAT_BLACKHOLE_PARTICLE`
   (`particles/builtin-particle`, additive). Driven by the existing
   `InfiniteWorldManager.suctionLoad` signal; ships with `rateOverTime = 0` so an
   idle singularity emits **exactly zero**. Cocos 3.8.3 has no radial-inward
   particle module, so a **negative `startSpeed`** reverses the circle emitter's
   outward vector into a genuine inward pull.
   *Defect found by measurement:* the emitter plane at y 0 sat inside the opaque
   body cylinder and the effect renders `depthTest: true`, so every particle was
   depth-culled **while still reporting a live emission rate**. The plane now
   clears the highest layer at every level.
2. **Rim energy** — authored `RimEnergyRing.glb` (two thin tori) +
   `MAT_BLACKHOLE_RIM` (additive). A second opaque ring would just be another flat
   torus; the blade spins one way, the halo counter-rotates.
3. **Rotation** — the per-frame spin from PHASE 2 was running but produced **no
   visible change**: every layer is a torus in the XZ plane, so it is rotationally
   symmetric about the Y axis it was being spun around. The layers were also
   nearly coplanar. `VORTEX_LAYERS` now gives each layer a non-zero X/Z tilt,
   opposite spin for neighbours, and a vertical funnel spread, with `HoleRing`
   kept flat as the stable horizon.
4. **Devour scale** — a decaying pulse per real absorption, deliberately **never**
   applied to `AbyssBase`/`HoleInner`: those are the structural body the gated
   `playerWidthRatio` silhouette is measured from, so scaling them would make a
   camera-framing gate move with a gameplay event.
5. **Level appearance** — `MACHINE_EVOLUTION_CONFIG` already declared
   `baseColor`/`rimColor` per level but nothing read them for the singularity.
   They now drive rim hue, rim-energy colour, particle colour and rate, vortex spin
   and funnel depth. `applyCoreSkin` still wins over the level palette.

### Screenshots I inspected myself

`artifacts/qa/portrait/portrait-390x844-singularity-lv1-zoom.png` — a tilted white
ring visibly sweeps **in front of** the black core (the vortex read), with a
distinct cyan additive glow band separate from the opaque lavender `HoleRing`.

`artifacts/qa/portrait/portrait-390x844-singularity-suction-zoom.png` — cyan
particle orbs arcing inward over the disc with a `+60` absorb popup, i.e. the
emitter running from real suction.

### Honest limits

- Additive rim saturation washes the level hue toward white/pale-yellow over
  bright ground, weakening the level-colour cue.
- Particle legibility is subtle at real rates (~20–35 live particles).
- The funnel depth is only ~0.17 m (~5 px at the gameplay camera); the vortex read
  comes from the **tilt**, not the height.
- **No LV5 screenshot was captured** — that needs the long `progression` scope.
  LV2–LV5 differentiation is verified as data (5 distinct rim colours/rates/spins/
  funnels, monotonic) plus the runtime tint mechanism proven at LV1.
- `GameManager.applySavedCoreSkin()` always applies `SKINS_CONFIG[0]`, so in the
  shipped build the level-driven *core body* hue is masked by design; the level
  shows through the rim energy, particles, spin and funnel.

## 6. PHASE 3 — NOT done, and it should not be done as written

**The brief asks for six static `.scene` files** (`city_center`, `residential`,
`warehouse`, `supermarket`, `construction`, `parking`).

**This conflicts with the game's architecture.** The world is an infinite
streaming X/Z grid. `InfiniteWorldManager` generates cells deterministically from
`DistrictTemplates.ts`, which already defines **7 district kinds**
(`RESIDENTIAL, PARK, SUPERMARKET, WAREHOUSE, PARKING, CONSTRUCTION, DOWNTOWN`),
and each cell is populated from authored `WorldArtLibrary` templates. There is one
`Game.scene` plus one `Bootstrap.scene`.

Six static scenes would **fork the world into two systems**: a streamed world and
six hand-built ones, with no defined relationship. It would not make the game more
asset-driven — the cell contents are *already* authored assets — and it would
break the streaming tests.

**Recommended PHASE 3 instead:** make each district an authored **cell prefab**
(not a Scene), which is the correct unit for a streaming game. The existing
`GoldenCityCell.prefab` is already the proven pattern for this — it is the authored
opening cell, placed in Creator, with its composition recorded in
`OPENING_CELL_COMPOSITION`. The work is: author one cell prefab per district kind,
and have `InfiniteWorldManager` instantiate the district's prefab instead of
generating geometry in code. That keeps streaming, keeps the tests, and delivers
exactly what the brief is reaching for — artist-editable maps.

**This is a scope decision the project owner should confirm** before it is built,
because it changes the shape of the deliverable.

## 11. Remaining issues and risks

1. **PHASE 3 is unresolved and needs a decision** (§6). It is the only phase where
   following the brief literally would damage the product.
2. **PHASE 5 and 6 are not started** (§7, §8).
3. **`OPENING_EDIBLE_SPREAD` is untested** (§2.1).
4. **The acceptance harness is non-deterministic** for gameplay-touch checks. It is
   documented in `cocos/docs/next-session-handoff.md`. I observed one flaky failure
   during PHASE 1 that did not reproduce; the harness was **not** modified.
5. **LV5 singularity appearance is verified as data only**, not screenshotted (§5).
6. **Additive rim saturation** weakens the level-hue cue on bright ground (§5).
7. `getAnimatedDecorationNodes()` now includes a node that only exists after the
   async asset adopts. It is rebuilt per call so it is correct today, but a future
   change that caches it would silently merge the rim energy into the gated
   silhouette.
