## 2. CONTROL FEEL

### 2.1 拖动手感根因（早期）

相机跟随硬编码 `dt * 5.0`，改为配置驱动的 `PLAYER_FEEL_CONFIG.cameraFollowSharpness = 18.0`。**根因在相机，不在玩家移动。**

### 2.2 位移不连续（本阶段首要任务）

**结论：不是 teleport，不是采样 bug，是 `CompressionSystem` 用过期快照把玩家拽回去。**

机制：

```
COMPRESSING  快照 compressionBasePosition = machine.position，并钉住机器
EJECTING     不写位置 —— 机器自由积分，玩家正常移动 0.45 秒
COLLECTING   setPosition(compressionBasePosition) ← 恢复 0.87 秒前的快照
```

算术吻合：`3.377 m ÷ 7.5 m/s = 0.450 s`；`3.229 m ÷ 7.175 m/s = 0.450 s`，而 `RESOURCE_DROP.durationSeconds` 正是 0.45 秒。

排查中**被数据否定**的假设：

| 假设 | 否定依据 |
|---|---|
| 浮动原点 rebase | 阈值 192 m，玩家当时仅 z≈-4；同一次运行中真实 rebase 表现为 `rebaseDelta=1`、`originDelta=202.386`（阳性对照） |
| 采样假象 | CDP 独立采样路径与引擎环形缓冲给出同一时间戳、同一数值 |
| 大 dt 积分 | 跳变方向与记录速度**相反**，积分只沿速度方向 |
| 回合开始重置 | `gameState` 全程 `PLAYING` |

修复：COLLECTING 时**只恢复 Y**（震颤只作用于 Y，机器自身积分只写 X/Z），X/Z 保留玩家真实位置。

### 2.3 Control 指标

| 指标 | 结果 |
|---|---|
| 取证运行 | 10 × 10 秒真实移动 |
| 结论 | `NO_UNEXPLAINED_POSITION_JUMP` |
| 未解释位移 | 0 |
| 最大非 rebase 位移 | 3.23 m → **0.40 m** |
| 控制台错误 | 0 |

### 2.4 取证过程暴露的一个测量错误

trace 的 `frameDt` 常常只有机器实际 `integrationDt` 的一半（采样节拍是机器更新率的 2 倍）。用 trace 的 dt 做上界会产生**每轮约 90 个假阳性**（`overBoundBy ≈ 1.3`）。改用机器自报的积分距离后全部消失。此前报告中"位移不连续"的噪声比例因此被高估。

## 4. 升级反馈

真实游玩帧同时包含：横幅 `升级！/ LV.2 磁力黑洞 / 解锁更大型目标 (现可吸附 T2 中型物件)`、HUD `LV.2 磁力黑洞` 与 `质量1090kg`、明显增大的黑洞本体。§11 要求的"横幅 / 黑洞变化 / 可吞 Tier 变化在同一次视觉事件里可理解"成立。

横幅门禁：`observedMaxActiveCount = 1`。此前该横幅**从未被任何测试覆盖**，且其 2.0 秒生命期短于验收快照的 3200 ms 等待，导致历史上任何截图都只能拍到它已消失。

### 死亡时间线（§15）

修复前：`gap = 0 ms` —— 玩家被吞与复活页弹出落在同一采样帧，即 brief 明令禁止的"Gameplay 正常 → 下一帧突然 Revive"。当时采到的 8 帧 "death" 序列**全部是复活页**，因为中间没有任何东西可拍。

修复后：`gap = 730 ms`。节拍帧内容：玩家黑洞已消失、两个吞噬者的 `危险 哨兵` / `危险 流光` 名牌仍在、HUD 显示 `第 8 / 8` 与 `240kg`、模态框尚未弹出。

节拍为**纯表现层延时**，不做任何 time-scale，因此比赛计时、冻结的复活倒计时与战斗权威均不受影响（§16 的约束）。

### 危险标记

`localThreatIds` 与**独立从 leaderboard 重算**的战斗规则完全一致（实测 `['bot-1','bot-2','bot-3','bot-7']`），名牌渲染为 `危险 蓝莓` / `危险 矿石` / `危险 风暴`。规则单一来源：`ArenaMatchManager.getLocalThreatIds()` 逐行对照 `updateCompetitorCombat`。

## 7. 已知问题

### 问题 1：Arena 开局平衡 —— 玩家从未成为猎手（待 owner 决策）

`timeToFirstChaseTarget` 与 `timeToFirstKill` 在**两次真实运行中均未到达**。战斗解锁（t=15 s）时本地玩家质量 240，而四个对手全部已超过 `CONSUME_RATIO`(1.32) 阈值。因此"追击 → 击杀 → 击杀反馈"这半个环路**在当前平衡下无法被触发**，§14 与 §17 也就无从验证。

这不是规则 bug，是"开局起始优势"的产品决策。

### 问题 2：危险预警提前量仅约 0.4 秒（需权衡）

一次运行中威胁列表在死亡前 **361 ms** 才出现；另一次整个存活期未采到。二者不矛盾：标记要求对手进入 `GRAVITY_RANGE`(4.8)，而击杀发生在 `CONSUME_RANGE`(1.28) 且需 `pullSeconds >= 0.8`，窗口天然只有几百毫秒。标记正确，但人类来不及反应。轮询分辨率约 330 ms，故 0.4 秒应视为**上限**。

若要提前预警，需放宽触发距离，这与 §13"只有真实危险状态才显示"相冲突，需 owner 定取舍。

### 问题 3：压缩期间 0.42 秒控制冻结（待 owner 决策）

`COMPRESSING` 期间机器被钉在原地，玩家失去约 0.42 秒控制；吸收频繁时每 0.87 秒循环一次。看起来是有意设计，但对手感是实打实的损失。

### 问题 4：network arena 的危险标记失效

`toNetworkArenaSnapshot` 中 `localThreatIds` 硬编码为 `[]`。网络局不跑本地战斗计算，无威胁数据可推，因此"知道谁危险"在网络局不生效。

### 问题 5：名牌重叠

多个对手聚集时，危险名牌投影坐标几乎重合（实测 x 差 < 0.07、y 差 < 0.2），互相压叠。

### 问题 6：验收 PASS ≠ 类型检查通过

本阶段曾出现"验收 PASS 但 `typecheck:cocos` 报错"的情况：Cocos 构建只转译不做完整类型检查。**"验收通过"不能作为类型正确的证据**，两者必须分别执行。
