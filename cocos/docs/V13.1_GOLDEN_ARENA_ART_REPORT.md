## 2. V13 原始视觉缺陷（本阶段查实的根因）

这一节是本报告最重要的部分，因为**上一阶段报的"竞技场构图改进"其实一个像素都没画出来**。

### 2.1 克隆出来的每一个节点都是空的（根因）

`scripts/author_supermarket_content.py` 的 `clone_subtree()` 里：

```python
mapping[id] = len(scene.arr)      # ← 在 collect() 期间求值
```

而元素是在 `collect()` **之后**才 append 的，所以 collect 期间 `len(scene.arr)` 是个常量——
**整个映射塌缩成同一个 id**。随后重写引用时，每个元素的引用都写进同一个槽位，
最后一个元素（叶子网格节点）胜出，于是克隆体拿到 `_children=[]`、`_components=[]`。

**实测后果**（在已发货的 `Supermarket.prefab` 上数出来的）：

| 分组 | 子节点数 | 真正有 MeshRenderer 的 |
| --- | ---: | ---: |
| Buildings | 19 | **13** |
| Park | 6 | 6 |
| Props | 44 | **14** |

也就是说 **V12/V13 加进竞技场的每一个簇、每一个争夺区道具、每一栋"画面边缘楼排"都不渲染**。
当时报告为"构图改进"而色桶几乎不动——**这正是"不可见几何"该有的样子**。

修法：id 改为 `base + 在 order 中的位置`，并且**写入前断言每个克隆体都带 MeshRenderer**，
否则拒绝写盘。

### 2.2 相机可见地面是窄梯形，不是 ±31

`scripts/probe_arena_ground_frustum.mjs` 用**射线打到 y=0** 量出来：

| 屏幕位置 | 可见世界范围（相对玩家） |
| --- | --- |
| 画面中高 | x **−10.0 .. 10.0** |
| 画面上缘（远） | x −14.0 .. 14.0 |
| 画面下缘（近） | x −7.8 .. 7.8 |
| 纵深 | z −40.8 .. 16.8 |

**`V13_ART_DIRECTION.md` 里写的"画面边界实测 x −31..31"错了三倍**——那个数是从地面几何量出来的，
不是视锥。所以第一版构图计划把 41 个建筑放在 `|x| = 20.5..28`，**全部在视野外**，而计划表打印得很干净。

### 2.3 另外三项

- **Props 里有 10 组重复子树**，每组两份在同一坐标（脚本跑两次的产物，因为克隆体保留源名、
  "已存在"检查永远匹配不上）→ 白费 draw call 与 z-fighting。
- **4 个模型沉进路面**：`delivery-van` 沉 1.0 单位（约 6px，看得见），
  `sedan`/`garbage-truck`/`tire` 沉 0.3。模板在 y=0，而 `setRoutePosition` 只传 x/z。
- **6 个 SpawnPoint 在相机画面外**（z 11.4–15.6 > 上限 11）→ 1/4 的可吞物在竞技场里永远看不见；
  **两栋楼内缘伸到半径 12.63**（对手在半径 14 出生）→ 对手会出生在楼里；
  **一栋办公楼立在路中央**（(0,−22)，`RoadSouth` 覆盖 x[−6,6] z[−24,−8]）。

## 4. Arena Before / After

**Before**（本阶段开始时）：路两侧只有画面边缘几个土黄盒子，中景是一大片路面，近场只有路。

**After**（`artifacts/qa/v13/arena/arena-390x844.png`）：
路两侧**成排建筑**紧贴路缘（0.75 单位路肩），建筑**颜色按行轮换**（克隆源不同则材质不同），
中景有后排建筑形成纵深，远端有楼封住视线，路缘有行道树与停放车辆。

关键约束（全部实测，不是假设）：出生环半径 11.8–16.2 不得有静态体；不在路面上；在画面内。
每一个槽位在写入前校验，所以被否的方案不可能半途落地。

**诚实的边界**：画面近端约 40% 仍是路面。这是**结构性**的——路宽 12 单位，
而可见带只有 20 单位宽；同时出生环挡住了 `|x|≈8.5` 处 `|z| < 16` 的整段。
要改变它需要动路面宽度或出生环，两者都会破坏玩法，所以本阶段没有动。

**色桶数在画面明显变好的同时从 400 降到 386** —— 这正是指令里那句
「禁止仅凭色桶数判断美术合格」。色桶是辅助指标。

# 附：2026-10-20 门禁修复与剩余产品决定

记录一次把失效门禁修到真实数字之后剩下的**产品决策**，以及为什么没有自行改动 `status: LOCKED` 的契约。

## 已修（本轮，未降低任何阈值）

1. **`FAIL_GOLDEN_CITY_SOURCE` 自 2026-10-12 起必失败。**
   竞技场在 `b850644` 明确改到 cell (6,0)（超市区），而门禁仍要求
   `currentCellSource === 'AUTHORED_GOLDEN_CITY'`。断言已改为"构图必须在真实开放的
   cell 上被测量"（`targetCell.key` 形如 `x:z`，且源属于两种 authored cell 之一）。
   探针自己的注释也写明"量的是玩家所站的那一格"，与断言现在一致。
   `--scope=full` 不经过这段代码，所以一个月来没有任何东西暴露它。

2. **探针把逻辑坐标投进了局部相机。** `collectibleSlots` 存的是"世界坐标 + logicalOrigin"
   （各写入路径一致），而 gameplay 相机在 cell 局部空间。于是 24 个 authored 槽位
   全部投到屏幕 x≈8400：报告"0/24 可见"，而同一批槽位在画面里渲染得好好的
   （实测 screen x 59–71）。改为投影前减 `logicalOrigin`，与重生系统的算法一致。
   可见数 0 → 13。

3. **四个槽位组在梯形视锥外。** 合同要求 ≥20 个可见 authored 槽位、≥2 个可见簇；
   实测 13。四个组（delivery-boxes / cart-return-litter / produce-discard /
   parking-recycling）authored 在 |x| 11.2–18.8，而 z −11..−19 处梯形半宽只有 10.0–11.8。
   新增 `scripts/author_arena_collectible_framing.py`：按 0.25 网格求最小整体平移，
   并用 `author_arena_composition.py` 的同一套规则复核（不压路、七出生点各留
   SPAWN_BODY_CLEARANCE=3.0、在视锥内、不与既有槽位重叠）。
   第一版平移把三个槽位推进 `SupermarketBuilding` 的剪影里，被遮挡检查抓到，
   于是把遮挡判据从"建筑 footprint"升级为门禁自己的判据（沿相机前向更深 + 屏幕 x
   落在其跨度内），并纳入全部静态遮挡物（4 栋楼、12 棵树、1 段围栏）。
   最终 24/24 可见、8/8 簇可见。

## 剩下的：7 项语义，是产品决定，不是本轮该改的

`design-contracts/golden-city-composition.json`（`status: LOCKED`）要求 12 项语义全部在场。
竞技场画面（73 个节点名）缺 7 项：

    shop / hospital / park / fountain / trees and flowerbeds / benches / bins

已查证：这些是**混合用途"黄金城"布景**的属性，与七张城区 prefab 不是一回事。
逐个 prefab 统计可映射语义，最高 6/9（Park、Residential 各 6），没有任何一格城区
同时具备全部 9 项名称可映射语义。开盘 cell（`acceptance:p0b` PASS、含
`ClusterAnchor_CentralPark`、Park/Fountain/Bench 命名节点）才有这套布景，
而竞技场从 `b850644` 起不再打那一格。

**因此这是二选一的所有者决定，不是缺陷清单：**

- **A. 契约按 cell 类型分派语义**：城区格满足"道路/树/灯/车/簇/竞争者"，
  黄金城布景格满足全部 12 项。需要契约变更与所有者签字。
