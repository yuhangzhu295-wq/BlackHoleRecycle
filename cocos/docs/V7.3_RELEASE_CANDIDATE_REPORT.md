## 2. BLOCKER — the WeChat main package is 11 MB against a 4 MB limit

Measured on the current build (`cocos/build/wechatgame`, built 2026-10-03 18:43):

| | Size |
|---|---|
| **Main package** | **11 MB** |
| `assets/` inside main | 7.3 MB |
| `cocos-js/` (engine) | 4.0 MB |
| `src/` | 0.26 MB |
| Subpackages (`world-construction`, `world-city`) | 5 MB |
| Total | 17 MB |

WeChat mini-games cap the **main package at 4 MB** (total across subpackages is
the larger budget). 11 MB is ~2.75x over, so this build cannot be submitted as
is. The two subpackages already exist and are wired correctly; the problem is
what remains in the boot package.

Largest files in the main package:

| File | Size | Note |
|---|---|---|
| `cocos-js/_virtual_cc-*.js` | 3.01 MB | the engine |
| `assets/main/native/9b/…@77daa.png` | **1.18 MB** | the unused bulldozer chassis texture — see §3 |
| `assets/internal/import/0b/…json` | 0.58 MB | engine builtins |
| `assets/main/native/6b/…png` | 0.45 MB | |
| `cocos-js/assets/bullet.release.wasm` | 0.45 MB | physics |

**Recommended fix path, in descending payoff:**

1. **Engine separation.** Cocos can move the engine out of the main package
   (WeChat's engine-plugin mechanism). This alone accounts for ~3-4 MB and is
   the single largest lever. It is a build-configuration change and does not
   touch game code.
2. **Move deferrable assets out of the boot package.** `assets/` is 7.3 MB in
   main. The boot package needs only what the launch scene and the player
   machine require; district art, collectible art, UI pages and `game-art`
   (materials, prefabs, maps, ui — ~0.86 MB) are candidates for subpackages.
   **This needs an owner decision**: which assets may be deferred without
   hurting the first-playable frame.
3. **Remove the unused 1.18 MB texture** (§3) — a cheap 1.18 MB, but note it is
   ~11% of the problem, not the fix.
4. **Texture compression** for the remaining PNGs (0.45 MB each and up).

**I did not implement any of this.** 1 and 2 are packaging-strategy decisions
with a real product trade-off (first-load experience), and 3 alone does not
move the blocker. They are recorded here as the release decision input.

## 3. The unused bulldozer texture (SOURCE_CHILD_UNUSED)

`cocos/assets/art/machines/poly-google-bulldozer.glb` embeds one image,
`Bulldozer_BaseColor`, a PNG of **1,236,674 bytes**, referenced by its single
material `blinn1SG` as `baseColorTexture`.

At runtime the machine never renders it: `MachineVisualLibrary.ts:77` applies
`getMaterial('chassis', null, MACHINE_ASSEMBLY_PALETTE.chassis)` — the texture
argument is `null`, and the chassis renders as a flat palette green. The
acceptance material diagnostics confirm the LV1 chassis as `builtin-unlit`
with a colour and no texture.

It still ships because `MachineVisualLibrary.ts:22` declares
`@property(Texture2D) bulldozerColorTexture` and `validate()` (line 53) throws
if it is null. So the asset is referenced — which is enough to pack it — but
not used for rendering. This is exactly the `SOURCE_CHILD_UNUSED` case, not a
`MISSING_RUNTIME_ASSET`.

Cleaning it up therefore means three coordinated edits: strip the image and its
bufferView from the GLB, drop or relax the `bulldozerColorTexture` property and
the `validate()` requirement, and re-verify the chassis still renders. It is
worth doing as part of the packaging work in §2, not as a standalone change.

## 6. Process findings worth carrying forward

1. **The visual-review subagent cannot see images in this environment.** Four
   probes: `architecture-reviewer` (`claude-sonnet-4-6`) and `general-purpose`
   both return *"Media omitted from provider request because the selected model
   does not support image input"*; `ui-builder` (`gpt-5.6-luna`) fails to start
   with `Model unavailable`; `deep-reasoner` (`gpt-6-astra`) fails with
   `Provider unavailable`. **All pixel review this round was done by the
   orchestrator.** Until the agent models are reconfigured, the visual line has
   a single point of failure.
2. **Evidence-capture scripts do not rebuild.** They serve the existing
   `cocos/build/web-mobile`. This produced a round of screenshots taken from a
   pre-edit build, and an implementer report whose arithmetic was
   self-consistent while the frame was unchanged. Every evidence claim now
   carries a `source mtime < build mtime < capture mtime` chain, and built
   scene JSON is decoded to confirm the new values actually shipped.
3. **Transform arithmetic is not verification.** Four separate defects this
   round were "numerically fixed, visually unchanged" — three of them on the
   same two pages. Layout math and the rendered frame disagree often enough
   here that a screenshot is the only acceptable proof.
